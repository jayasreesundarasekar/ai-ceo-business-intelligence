# AI CEO — full-stack version

This app was originally a frontend-only demo: `src/lib/workflowEngine.ts` ran a
hardcoded "Complaint → Discount → Email" script against `src/data/mockData.ts`.
It's now a real full-stack app:

| Requirement | Where it lives |
|---|---|
| 1. Real open-source LLM | `server/src/llm/groq.ts` — every recommendation, risk score, and message is generated by an open-source model (Llama 3.3 via Groq's free hosted API) at request time, not hardcoded. |
| 2. Real agent workflow (8 steps) | `server/src/agent/pipeline.ts` — Slack event → customer history → sentiment → churn risk → LLM decides action → explanation → follow-up task → draft message. |
| 3. Real Slack integration | `server/src/slack/` — OAuth (`oauth.ts`), Events API (`events.ts`), slash commands (`commands.ts`: `/churn-check`, `/ask-ceo`, `/briefing`), interactive buttons (`interactive.ts`), all with real signature verification. |
| 4. Real data | `server/schema.sql` + `server/src/db/queries.ts` — Supabase/Postgres tables for customers, purchases, engagement, tickets, Slack messages, tasks, feedback, briefings. |
| 5. Memory | `conversation_memory` table — past events and agent decisions per customer are fetched and folded into every new LLM prompt. |
| 6. AI reasoning | The LLM call in `pipeline.ts` returns churn probability, risk level, recommended action, confidence, and a business explanation — all model-generated. |
| 7. Executive dashboard | `server/src/routes/dashboard.ts` computes metrics/revenue/churn/insights from the database; `src/pages/Dashboard.tsx` and `src/pages/Insights.tsx` fetch them live via `src/lib/api.ts`. |

### Extended vision (from the "Nexus AI" brief) — what's built and what isn't

| Idea from the brief | Status |
|---|---|
| AI CEO greeting / daily briefing | ✅ `GET /api/briefing/today` (`server/src/agent/multiAgent.ts`) — real narrative on `Dashboard.tsx`, cached per day in `daily_briefings`. |
| Real Slack Q&A ("which customer is most likely to leave?") | ✅ `/ask-ceo` Slack command + `POST /api/knowledge/ask` (`server/src/agent/knowledgeBase.ts`) — real keyword search over tickets/Slack/agent history feeding a grounded LLM answer. |
| Autonomous decision engine | ✅ `pipeline.ts` — already covered above. |
| AI memory ("I remember...") | ✅ `conversation_memory`, read on every decision. |
| Business timeline (live feed) | ✅ `GET /api/timeline` + `src/pages/Timeline.tsx`. |
| Explainable decisions | ✅ `business_explanation` field, generated per decision, shown in the UI and Slack messages. |
| Multi-agent system (Finance/Sales/Support/Marketing → CEO) | ✅ `server/src/agent/multiAgent.ts` — four real, distinct LLM calls run in parallel, then synthesized by a fifth "CEO" call. Powers the daily briefing. |
| Predictive analytics | ⚠️ Partial, by design. `GET /api/forecast` (`server/src/agent/forecast.ts`) gives revenue/churn/ticket-volume forecasts reasoned by the LLM over real historical rows — explicitly disclosed as an LLM estimate, not a trained statistical model. There's **no** employee-burnout prediction, because this schema has no HR/headcount data to reason over; fabricating that number would be worse than omitting it. |
| Live dashboard from real data | ✅ Covered above. |
| Voice mode | ❌ Not built. The brief itself calls this optional/bonus, and it needs a speech-to-text/TTS pipeline that's a separate scope of work from everything else here — flagging rather than half-implementing it. |
| Executive reports (PDF, one click) | ✅ `GET /api/reports/weekly` (`server/src/routes/reports.ts`, via `pdfkit`) — streams a real PDF built from live metrics + today's briefing. Wired to the "Generate Now" button and the featured report's "PDF" button in `Reports.tsx`; the three older report rows are still illustrative placeholders (same pattern to extend if you want full history). |
| Business knowledge base across Slack/CRM/tickets/emails | ⚠️ Partial, honestly scoped. Searches everything actually *in this schema* — tickets, Slack messages, agent decisions, memory. There's no email or external CRM ingestion here (no credentials/API for that exist in this project), so questions about sources outside this database won't have anything to retrieve. |
| Learning system (adapts to rejected recommendations) | ✅ `decision_feedback` table, populated by Slack Approve/Dismiss clicks; the next decision prompt includes historical approval rate per action type. This is prompt-level adaptation, not model retraining — an LLM-based agent doesn't have weights to fine-tune here. |

## Running it

1. **Backend** — follow `server/README.md` in full (free Groq API key, Supabase
   project + schema, Slack app creation, optionally ngrok). Then:
   ```bash
   cd server && npm install && npm run dev
   ```
2. **Frontend**:
   ```bash
   cp .env.example .env      # set VITE_API_URL if the backend isn't on :8787
   npm install
   npm run dev
   ```
3. Open the app, go to **Live Demo**, and send a message like
   `"XYZ Corp is unhappy with response times"` — it now runs the real
   pipeline against Groq's hosted model and your Supabase data instead of a
   canned script.

## What's genuinely wired end-to-end vs. still a starting point

- **Fully wired**: Live Demo (`WorkflowContext` → `runWorkflow` → backend
  `/api/workflow/trigger` → Groq + Supabase), Dashboard, Insights, Slack
  connection status/OAuth.
- **Backend-complete, frontend still illustrative**: the channel-subscription
  toggles and historical report list on the Slack/Reports pages are UI-only —
  wire them to `tasks`/`workflow_runs` queries the same way Dashboard.tsx
  does if you want them live too. The pattern in `src/lib/api.ts` +
  `Dashboard.tsx` is the template to copy.
- **Needs your own credentials, can't be done from here**: the actual Slack
  app (Client ID/Secret, signing secret), a free Groq API key, and a
  provisioned Supabase project — all documented step-by-step in
  `server/README.md`.
